# RR 引导排障手册

> 目标：当 Synology Assistant 找不到黑群晖时，用最少的假设、最快的观测，判断问题在哪一层。
> 核心原则：**先证明「NAS 有没有发包」，再谈 Assistant、防火墙、DHCP。**

---

## 1. 第一原则：把「找不到」翻译成可观测事实

Synology Assistant 的工作方式很简单：在局域网里广播/组播发现报文，等 DSM 回应。它找不到，只说明「没收到回应」，不能直接推出是谁的问题。

先建立一个二分：

```
NAS 有没有发出任何二层报文？
├─ 没有 → 问题在 NAS 自身：供电 / POST / 引导介质 / 引导项 / 内核
└─ 有   → 问题在网络路径：VLAN / 端口隔离 / DHCP / 网段 / 防火墙
```

判断「有没有发包」最可靠的位置是 **DHCP 服务器 / 网关的链路层**，而不是 Assistant 的界面。

### 1.1 三个常见误判

| 观测 | 能证明 | 不能证明 |
|---|---|---|
| 网口 link 灯常亮 | 网线两端 PHY 协商成功 | 操作系统起来了、网卡驱动加载了 |
| 网口 act 灯闪 | 有电信号/链路活动 | 一定是 NAS 在发业务包（可能是对端在发） |
| 交换机/路由器端口亮灯 | 物理链路存在 | 设备在同一个二层域（iTV / WAN 口会打破这个假设） |

### 1.2 四组互相印证的证据

本案例中，以下四组证据同时指向「NAS 零发包」：

1. **全段扫描**：`192.168.10.0/24` 只有网关、电脑、MacBook、Watch，无 NAS。
2. **DHCP 租约日志**：唯一 DHCP 服务器上没有任何 NAS 的 DISCOVER/REQUEST。
3. **另一网段扫描**：`192.168.1.0/24` 只有已失效的网关管理地址。
4. **mDNS/Bonjour**：`_device-info._tcp`、`_http._tcp` 零响应。

四组独立观测同时为负，才可以把「网络配置问题」排除掉。

## 2. 四层决策树

从下往上查，任何一层为「否」，都不要跳到上一层。

### L0：供电与 POST

| 观测点 | 正常 | 异常含义 |
|---|---|---|
| 风扇 | 转 | 不转：电源/主板 |
| 蜂鸣器 | 短促一声 | 没有：可能没 POST |
| 硬盘 | 轻微震动 | 不转：供电或 SATA 未初始化 |
| 前面板电源灯 | 常亮/规律闪烁 | 不亮：没上电 |
| USB 键盘 Caps Lock | 能切换 | 不亮：没 POST 或已死机 |

Caps Lock 是一个便宜且可靠的「机器是否活着」探针：BIOS 或 Linux 都会响应键盘 LED。

### L1：引导介质

| 检查 | 正确做法 | 典型错误 |
|---|---|---|
| 镜像写入方式 | DD / raw（BalenaEtcher，或 Rufus 选 DD） | Rufus ISO 模式：能识别、能亮灯，但 BIOS 不引导 |
| USB 口 | 主板**后置 USB 2.0**（黑色） | 前面板线没接、USB 3.0 口老 BIOS 不认 |
| BIOS 启动项 | U 盘在 `Boot Option #1` | CMOS 电池没电后启动顺序回默认 |
| 引导模式 | 与上次成功时一致（本例为 UEFI） | 混用 UEFI/Legacy，或 CSM 状态改变 |
| SATA | AHCI | IDE/RAID 模式导致 DSM 认不到盘 |

**法证技巧**：RR 会在 U 盘 `boot/grub/rsysenv` 里写入上次引导时采集的硬件信息：

```
rr_booting=Boot Type: [UEFI] [USB flashdisk]
sys_cpu=Intel(R) Celeron(R) CPU  J1900  @ 1.99GHz
sys_mem=3806 MB
sys_dmi=... Aptio CRB, BIOS 5.6.5 12/20/2018
```

如果这些信息与目标机器一致，说明**这个 U 盘曾经在这台机器上成功引导过**。那么问题就不在 U 盘或镜像，而在「这次为什么没引导它」。

### L2：引导项

RR 的 GRUB 菜单通常有两类入口：

| 菜单项 | 实际行为 | 适用场景 |
|---|---|---|
| `Boot DSM` | 加载 `/bzImage-rr` + `/initrd-rr`，进入 **RR 环境（TinyCore）** | 配置、编译引导、救援、首次安装 |
| `Boot DSM kernel directly` | 加载 `/zImage-dsm` + `/initrd-dsm`，直接 `root=/dev/md0` 引导硬盘上的 DSM | 已配置完成、追求最快启动 |

**关键认知**：`direct` 路径跳过 RR 环境。RR 环境负责拉起网络、生成 cmdline、`kexec` 进 DSM。跳过它，很多准备工作没有做，DSM 内核可能停在很早的阶段。

而 DSM 内核的日志走 `console=ttyS0,115200n8`（串口），VGA 上只显示 `Booting...` 就不再输出。**看起来像死机，实际日志在串口里**。

### L3：网络路径

| 检查 | 说明 |
|---|---|
| 是否插在 iTV 口 | 光猫的 iTV 口是独立 IPTV VLAN，灯亮、链路通，但主 LAN 完全看不到 |
| 是否插在 WAN 口 / 2.5G 自适应口 | 可能落在 WAN 侧，与 LAN 隔离 |
| 是否与 DHCP 服务器同二层 | 跨网段、跨 VLAN、AP 隔离都会导致发现失败 |
| 直连电脑验证 | 排除光猫/交换机/端口绑定，只看 NAS 自己发不发包 |

**直连测试的判读**：

- 链路 1 Gbps：说明网线四对线全通，物理层没问题。
- 20 秒内单播/广播/组播计数全部 `+0`：**PHY 起来了，但操作系统没有把网卡跑起来**。
- 只要有一个方向持续增长，就说明系统活着，问题在网络路径而不是引导。

## 3. RR 引导的两个关键开关

配置文件在 U 盘根目录：`user-config.yml`。

```yaml
directboot: "true"    # 是否跳过 RR 环境，直接引导 DSM
bootwait: "10"        # RR 环境等 IP 后，进入 DSM 的倒计时（秒）
bootipwait: "10"      # RR 环境等 IP 的时间（秒）
```

### 3.1 启动流程

```
BIOS/UEFI
  └─ GRUB
      ├─ Boot DSM  →  /bzImage-rr + /initrd-rr  →  RR 环境 (TinyCore)
      │                ├─ 拉起网络，等待 IP（bootipwait）
      │                ├─ 启动 SSH(22, root/rr)、ttyd(7681)、菜单(7080)、DUFS(7304)
      │                ├─ _bootwait 倒计时（bootwait）
      │                └─ 倒计时结束 → kexec /zImage-dsm + /initrd-dsm → DSM
      │
      └─ Boot DSM kernel directly  →  /zImage-dsm + /initrd-dsm
                                       root=/dev/md0, console=ttyS0
                                       → 跳过 RR 环境的所有准备
```

### 3.2 只改 `directboot` 为什么不够

这是本案例最重要的一个发现。

网上多数说法是「把 `directboot` 改成 `false` 就能停在 RR 环境」。但读 RR 的 `boot.sh` 会发现：

1. `directboot=false` 只是**不立即**引导 DSM。
2. 它仍然会先拉起网络、等 IP，然后进入 `_bootwait` 倒计时。
3. **倒计时默认只有 10 秒**，结束后照样 `kexec` 进 DSM。
4. 10 秒内人来不及打开浏览器、更来不及完成配置。

`_bootwait` 有一个中断条件：**倒计时期间有新的 SSH / Web 会话接入，或打开菜单，就会中止引导并停在 RR 环境。**

所以正确的最小改法是两项一起改：

```yaml
directboot: "false"
bootwait: "300"      # 留出 5 分钟窗口；稳定后可降到 30~60
```

改完后，开机流程变成：

```
GRUB → RR 环境 → 网络起来、DHCP 拿地址 → 300 秒窗口
     → 你在窗口内 SSH / 打开 7681 → 倒计时中断，停在 RR 环境
     → 诊断/修复完成 → 手动或等待倒计时结束 → kexec 进 DSM
```

### 3.3 不要动 `grub.cfg`

U 盘根目录的 `grub_cksum.syno` 内容类似：

```
/zImage Encrypted: 830e4e0b
/rd.gz Encrypted: fc21bd0
```

它校验的是 **DSM 内核和 ramdisk**，不是 `grub.cfg`。改 `grub.cfg` 不会触发这个校验，但也没有必要：

- GRUB 默认项本来就是 `boot`（RR 环境），除非 `grubenv` 里有 `next_entry` 或默认项被改成 `direct`。
- 真正让机器跳过 RR 环境的是 `directboot: "true"`，不是 GRUB 默认项。

**结论：只改 `user-config.yml`，不动 `grub.cfg`。**

### 3.4 配置修改的安全做法

1. 先备份原文件（例如 `user-config.yml.bak`）。
2. 只替换目标两行，保留引号和缩进。
3. 写回后逐行 diff，确认**只有目标行变化**。
4. 记录文件字节数变化（本例 7866 → 7868，正好 +2）。

`tools/patch_rr_config.py` 已把这套流程脚本化。

## 4. 无显示器恢复流程

适用：没有显示器、没有串口、没有 IPMI，只有一台 Windows 笔记本。

### 4.1 拓扑准备

```
        Wi-Fi（保留远程/上网）
电脑 ──────────────────────── 路由器 / 手机网关
  │
  └── 有线网口 ──── 网线直连 ──── NAS
```

要点：

- **先把电脑切到 Wi-Fi**，确认默认路由和公网都正常，再拔有线网线。否则一拔就断远程。
- 电脑有线网口会拿到 `169.254.x.x` 链路本地地址，这是正常的（直连没有 DHCP）。
- NAS 网线不要插 iTV / WAN 口；直连时这些都不参与。

### 4.2 步骤

```bash
# 1. 改 U 盘配置（先备份，再改，再校验）
python tools/patch_rr_config.py --config "<U盘>/user-config.yml" \
    --directboot false --bootwait 300 --apply

# 2. 在电脑有线网口上启动最小 DHCP 服务
#    注意：offer IP 必须避开 ZeroTier / Hyper-V / WSL 的虚拟网卡地址
python tools/dhcp_server.py \
    --server-ip 169.254.10.1 \
    --offer-ip  169.254.10.3 \
    --duration  14400

# 3. U 盘插回 NAS 后置 USB 2.0，冷启动

# 4. 盯 DHCP 日志，识别是谁在要地址
#    RR 环境: vendor='udhcp 1.30.1'
#    DSM:     host='<主机名>'，可能会先请求旧静态 IP
```

### 4.3 DHCP 日志怎么读

| 报文特征 | 含义 | 下一步 |
|---|---|---|
| `vendor='udhcp 1.30.1'` | RR 环境（TinyCore）的 udhcpc | 窗口内 SSH `root/rr` 或打开 `:7681` |
| `host='<你的 DSM 主机名>'` | DSM 内核/系统已起来 | 等 5000/5001 端口，浏览器登录 |
| `mac` 是电脑自己的网卡 | Windows 在链路上重试 DHCP | 忽略，不要自己给自己发 OFFER |
| 只有 DISCOVER、没有后续 | 对端没收到 OFFER，或防火墙挡了 | 检查 Windows 防火墙入站规则 |
| 请求的是旧网段地址（如 `192.168.1.248`） | DSM 里存着旧静态配置 | 发 NAK，让它接受新地址 |

### 4.4 进入 RR 环境后

RR 环境默认提供：

| 服务 | 端口 | 凭据 |
|---|---|---|
| SSH | 22 | `root` / `rr` |
| ttyd 终端 | 7681 | 无 |
| HTTP 菜单 | 7080 | 无 |
| DUFS 文件 | 7304 | 无 |

常用诊断命令：

```bash
uname -a
cat /proc/cmdline
cat /proc/partitions
lsblk -o NAME,SIZE,TYPE,MODEL,SERIAL
ip -4 addr
w                      # 看有没有别的会话（会影响 _bootwait 中断）
ls /opt/rr             # RR 的脚本和工具
```

重点确认：

1. 硬盘有没有被识别（`lsblk` 里有没有那块系统盘）。
2. `root=/dev/md0` 对应的 md 设备是否存在。
3. 网卡是否拿到地址、默认路由是否正常。
4. 是否有足够的会话保持（SSH 连接本身就能打断倒计时）。

### 4.5 让 DSM 正常启动

- 在 RR 环境里确认磁盘和系统分区没问题后，等待 `bootwait` 倒计时结束，或手动触发引导。
- DSM 起来后会再次 DHCP，这次报文里带主机名。
- DSM 服务端口：`22`（SSH）、`5000`（HTTP）、`5001`（HTTPS）。
- 若 DSM 里存着旧网段的静态 IP，会先请求旧地址；DHCP 服务应回 NAK，让它接受新地址。

### 4.6 收尾

1. 把 NAS 网线从电脑拔下，插回路由器的 **LAN1/LAN2/LAN3**（避开 iTV / WAN / 2.5G 自适应口）。
2. 确认 NAS 从主网关拿到地址，`5000` 可访问。
3. **停掉电脑上的临时 DHCP 服务**，否则它会和主网关抢答，影响家里其他设备。
4. 把 `bootwait` 从 300 降到 30~60，减少日常开机等待。

## 5. 常见坑清单

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | Assistant 找不到，网口灯亮 | 灯只证明 PHY，系统没起来 | 抓 DHCP/ARP/mDNS，先证明有没有发包 |
| 2 | 换到 LAN1/2/3 仍然零包 | 引导项是 `Boot DSM kernel directly` | 改 `directboot: false` + `bootwait: 300` |
| 3 | 改了 `directboot: false` 还是进 DSM | `bootwait` 默认 10 秒，倒计时结束仍 kexec | 同时拉长 `bootwait`，并在窗口内建立 SSH/Web 会话 |
| 4 | 屏幕停在 `Booting...` | DSM 内核日志走 `ttyS0`，VGA 不再输出 | 不要等 VGA；从网络侧判断，或进 RR 环境看日志 |
| 5 | 插 LAN4 灯亮但完全不可见 | LAN4 是 iTV 口，独立 IPTV VLAN | 换 LAN1/2/3 |
| 6 | 断电后 BIOS 设置全丢、时间回到 2017 | CR2032 没电 | 换电池；BIOS 重设 U 盘启动；DSM 里校时 |
| 7 | U 盘在 Windows「此电脑」里看不到 | 分区类型 `0x83`，Windows 不分配盘符 | 用 `Get-Volume` / `\\?\Volume{GUID}\` 访问，或磁盘管理 |
| 8 | Rufus 写完不能引导 | 用了 ISO 模式 | 改用 DD / raw 模式 |
| 9 | J1900 不认 U 盘启动 | USB 3.0 口 / 前面板口 | 插主板后置 USB 2.0（黑色） |
| 10 | 直连后 ping 0ms、22 端口“打开”但连不上 | DHCP 地址和 ZeroTier/虚拟网卡撞了 | 换 offer IP；用 `Find-NetRoute` 确认走物理网口 |
| 11 | Python DHCP 收不到包 | Windows 防火墙对该 Python 解释器有入站 Block 规则 | 换一个有 Allow 规则的解释器，或加放行规则 |
| 12 | DSM 套件中心报「检查网络和时间」 | 时钟偏差 9 年，TLS 证书校验失败 | 先手动把时间改到当前，再开 NTP |
| 13 | NTP「立即更新」总是失败 | 偏移超过 1000 秒，ntpd 拒绝步进 | 先手动校时到接近当前，再让 NTP 接管 |
| 14 | 80 端口显示 `Your website is not set up yet` | 那是 Web Station 占位页 | DSM 管理界面在 `:5000` |

## 6. 恢复后的加固

1. **换 CR2032**：否则每次彻底断电都会丢 BIOS 设置和时钟。
2. **BIOS**：U 盘设为第一启动项，确认 UEFI/Legacy 与成功时一致，SATA = AHCI。
3. **`bootwait`**：救援完成后降到 30~60 秒；不要改回 `directboot: true`，除非你确认 direct 路径可用。
4. **时间**：DSM 控制面板 → 区域选项 → 时间，先手动校准，再启用 NTP。
5. **网络**：NAS 固定在 LAN1/2/3；给 NAS 做 DHCP 静态绑定，避免网关重启换网段后找不到。
6. **安全自查**：检查 Docker 端口映射是否有 `0.0.0.0:3306`、`0.0.0.0:6379` 这类不应暴露的服务；检查 SSH 是否对全网开放。

## 7. 方法总结

这套排障之所以能在没有屏幕的情况下收敛，靠的不是「多试几次」，而是三条纪律：

1. **每一层只问一个二值问题**：有没有 POST？有没有读 U 盘？有没有进 GRUB？有没有发包？有没有拿到 IP？有没有起服务？
2. **每个结论都要有独立证据**：至少两个不同位置、不同工具的观测互相印证。
3. **先排除观测点错误**：抓包抓错网卡、ping 到虚拟网卡、把 Web Station 当成 DSM，都会制造假阳性。每次换拓扑，先确认「我现在看的是哪条链路」。
