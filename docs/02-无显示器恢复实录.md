## 3. 证据链详解

### 3.1 「零包」是怎么定死的

单次抓包可能漏，所以做了多轮、多个位置、多个时间窗：

- 手机侧 `tcpdump`：5 分钟、4 分钟、7 分钟、10 分钟多轮。
- 手机 DHCP 租约日志：作为唯一 DHCP 服务器，它最有发言权。
- 全段 ICMP/ARP 扫描：两个网段。
- mDNS/Bonjour 查询：群晖开机必发。

四类观测、多个时间窗全部为负，才敢下「NAS 没发包」的结论。

**反例的价值**：同一时间窗里，MacBook、Watch、FTTR 的 SSDP 都清清楚楚。这说明抓包本身是有效的，不是工具坏了。

### 3.2 U 盘法证：`rsysenv` 证明它曾经能启动

RR 在引导时会把运行环境写入 `boot/grub/rsysenv`：

```
rr_booting=Boot Type: [UEFI] [USB flashdisk]
sys_cpu=Intel(R) Celeron(R) CPU  J1900  @ 1.99GHz
sys_mem=3806 MB
sys_dmi=... Aptio CRB, BIOS 5.6.5 12/20/2018
```

这条记录的价值在于：它把「U 盘/镜像/写入方式」全部排除了。**同一块 U 盘、同一台机器、同样的 UEFI 模式，曾经成功过。** 那么现在的问题只能是「这次为什么没引导它」。

同时核对了：

| 项目 | 值 | 判断 |
|---|---|---|
| RR 版本 | 26.3.0 | 正常 |
| 型号/平台 | DS918+ / apollolake | 正常 |
| DSM | 7.3 (86003) | 正常 |
| 引导文件 | EFI + Legacy 两套齐全 | 正常 |
| `directboot` | `true` | **可疑** |
| `grub_cksum.syno` | 校验 `/zImage`、`/rd.gz` | 与 `grub.cfg` 无关 |

Windows「此电脑」里看不到 U 盘盘符也一度引起怀疑，实际是分区类型 `0x83`（Linux），Windows 不自动分配盘符。用 `Get-Volume` 找到 `RR1` 卷，再通过 `\\?\Volume{GUID}\` 路径读取即可。

### 3.3 BIOS 复位：第一层根因

用户回忆：修电源时拔下 CMOS 电池看了一下，上电前又装回去。

CMOS 电池给主板 SRAM 供电，BIOS 的启动顺序、UEFI/Legacy 模式、SATA 模式、CSM、快速启动全存在里面。**哪怕只拔几秒，设置也会回到出厂默认。**

现象完全吻合：

- U 盘里的 `rsysenv` 证明它曾经从 U 盘成功引导。
- 拔电池后，启动顺序回到 SATA/网络，不再从 U 盘引导。
- 于是 NAS 连 GRUB 都没进，自然零包。

进 BIOS 后确认：BIOS 能认到 U 盘（`UEFI: VendorCoProductCode 2.00`），设为第一启动项后 GRUB 成功起来。**这一层解决后，才暴露下一层。**

### 3.4 iTV 口：第二层根因

用户一直把网线插在 FTTR 的 **LAN4**。该机型 LAN4 是 iTV 口，属于独立的 IPTV VLAN。

表现：

- 网口灯正常亮。
- 链路正常协商。
- 主 LAN 里一个包都看不到。
- DHCP 拿不到、ARP 不可见、Assistant 永远找不到。

这一层和 BIOS 是**独立**的：即使引导成功，插在 LAN4 上也还是不可见。两层必须都解决。

### 3.5 `direct boot`：第三层根因

BIOS 修好后，屏幕停在：

```
Booting `Boot DSM kernel directly'
Booting...
```

很多人会以为卡死了。实际是：

- `direct` 项跳过 RR 环境，直接加载 `/zImage-dsm` + `/initrd-dsm`。
- cmdline 里 `root=/dev/md0`，并且 `console=ttyS0,115200n8`。
- DSM 内核日志全部走串口，VGA 不再输出。
- 同时网卡没有起来，所以零包。

**终极验证**：把 NAS 网线直接插到电脑网口。

| 项目 | 结果 |
|---|---|
| 链路 | 1 Gbps，Connected |
| 20 秒单播 | +0 |
| 20 秒广播 | +0 |
| 20 秒组播 | +0 |

链路通、零发包 = PHY 起来了，操作系统没有把网卡跑起来。这排除了 FTTR、VLAN、网线、端口绑定的所有嫌疑，把问题锁死在 NAS 的引导路径上。

### 3.6 为什么 `directboot=false` 还不够

第一版方案只改 `directboot`。读 `boot.sh` 后发现不够：

- `directboot=false` 仍会进入 `_bootwait` 倒计时。
- 默认 `bootwait=10`，10 秒后照样 `kexec` 进 DSM。
- 唯一的中断方式是：倒计时期间建立新的 SSH/Web 会话，或打开菜单。

所以最终改了两行：

```diff
- directboot: "true"
+ directboot: "false"

- bootwait: "10"
+ bootwait: "300"
```

改完逐行 diff：480 行里只有这两行变化，文件从 7866 字节变成 7868 字节。备份保留在原项目目录。

## 4. ZeroTier 地址碰撞

这是整晚最隐蔽的一个假阳性。

DHCP 服务给 NAS 分配了 `169.254.10.2`。随后：

- `ping 169.254.10.2` → 0ms。
- 端口 22 → “OPEN”。

看起来 NAS 已经上线，但 SSH 认证总是超时，而且 DHCP 日志里没有 NAS 重新申请地址的记录。

查路由表发现：`169.254.10.2/32` 被 **ZeroTier 虚拟网卡**占用，走的是本地路由。也就是说，ping 和端口探测全是在和电脑自己说话。

**修复**：

1. 把 DHCP offer 改成 `169.254.10.3`。
2. 用 `Find-NetRoute -DestinationIP 169.254.10.3` 确认它走物理以太网口（`ifIndex <N>`），而不是虚拟网卡。
3. 重新冷启动，等待脚本挂到 `169.254.10.3`。

**教训**：直连场景下，`169.254.x.x` 很容易和 ZeroTier、Hyper-V、WSL、Docker 的虚拟网卡撞车。分配地址前先查路由，别只看 ping 通不通。

## 5. 恢复过程

### 5.1 进入 RR 环境

配置改好后，NAS 冷启动：

1. GRUB 默认进 `boot`（RR 环境）。
2. RR 环境拉起网络，向电脑的 DHCP 服务发 DISCOVER。
3. DHCP 日志出现 `vendor='udhcp 1.30.1'` —— 这是 RR 环境（TinyCore）的 udhcpc 特征。
4. 分配 `169.254.10.3`。
5. 在 `bootwait=300` 窗口内建立 SSH 会话（`root/rr`），倒计时被中断，停在 RR 环境。

### 5.2 DSM 启动

在 RR 环境确认磁盘识别正常后，让倒计时结束或手动触发引导：

- DHCP 日志出现 `host='<NAS-HOSTNAME>'` —— DSM 系统起来了。
- 它先请求了旧网段的静态地址 `192.168.1.248`，DHCP 回 NAK，随后接受 `169.254.10.3`。
- 22/5000/5001 端口开放。
- DSM 页面 HTTP 200，加载约 0.12 秒。

### 5.3 网络抖动

DSM 启动阶段出现「约 13 秒通、13 秒断」的固定节律。同步采样网卡计数后确认：

- 链路始终 Up。
- 断的时候不是链路断开，是 DSM 的网络服务在反复重启。

启动完成后消失。最终 60 次 ping 只丢 2 次，延迟 0~1ms。

### 5.4 回到家庭网络

把 NAS 网线从电脑拔下，插回 FTTR 的 LAN1/2/3：

- 手机网关的邻居表出现 NAS 的 MAC，状态 REACHABLE。
- NAS 拿到 `192.168.10.23`。
- 22/5000/5001 全部 OPEN。
- DSM 页面正常。

随后**立即停掉电脑上的临时 DHCP 服务**，避免和主网关抢答。

## 6. 后续问题：时间与套件中心

DSM 登录后，套件中心报「连接失败，请检查网络和时间设置」。

排查：

- NAS 的 DNS 正常（网关 `:53` 有应答）。
- 它已经和 Synology 服务器建立 TCP 443 连接。
- 5G 网络放行 NTP（电脑侧测四个 NTP 服务器都正常）。
- DSM 时间停在 **2017-07-24**，偏差 9 年。

根因：TLS 证书校验失败；同时 ntpd 默认拒绝超过 1000 秒的步进，所以「立即更新」永远失败。

处理：先关闭 NTP，手动把日期时间改到当前，应用后再启用 NTP。根治办法是换 CR2032。

## 7. 复盘：哪些判断被修正过

| 初始判断 | 后续证据 | 修正 |
|---|---|---|
| U 盘可能写坏了 | `rsysenv` 证明曾成功引导 | U 盘没问题 |
| 双网口插错 | 用户确认背面只有一个网口 | 排除 |
| 镜像用了 ISO 模式 | 用户确认 DD / BalenaEtcher | 排除 |
| 改了 `directboot` 就能停在 RR 环境 | 读 `boot.sh` 发现仍有 10 秒倒计时 | 必须同时改 `bootwait` |
| ping 通、22 端口开 = NAS 上线 | 路由表显示是 ZeroTier 地址 | 观测点错了 |
| 80 端口报错 = DSM 坏了 | 那是 Web Station 占位页 | DSM 在 5000 |

这些修正说明一件事：**排障时最危险的不是没有证据，而是证据指向了错误的观测对象。**

## 8. 可复用结论

1. 网口灯亮 ≠ 系统起来；link up ≠ 有包。
2. Assistant 找不到 ≠ Assistant 的问题；先在 DHCP/网关侧证明 NAS 有没有发包。
3. 老主板拔 CMOS 电池 = BIOS 设置清零；换 CR2032 是长期解法。
4. 光猫的 iTV 口是独立 VLAN；LAN4 尤其要避开。
5. RR 的 `direct` 路径会跳过网络准备；`directboot=false` 必须配 `bootwait` 才有操作窗口。
6. 无显示器时，PC 直连 + 最小 DHCP + RR 环境 SSH 是一条可靠救援路径。
7. 直连场景优先用 `169.254.x.x`，但必须先检查虚拟网卡地址冲突。
8. DSM 时间偏差过大会同时破坏 TLS 和 NTP；先手动校时，再让 NTP 接管。
